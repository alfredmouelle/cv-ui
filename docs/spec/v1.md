# CV UI V1 specification

Status: Normative implementation handoff.

This document defines the complete V1 acceptance contract for `cv-ui.alfredmouelle.com`. An implementation conforms only when every requirement in this document passes. Linked decision tickets provide rationale. They do not replace this contract.

The words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY have their RFC 2119 meanings.

## 1. Product boundary

V1 MUST provide:

- one shared CV Data V1 contract;
- one shared Fidelity Envelope;
- shadcn-compatible CV Registry Items;
- a searchable human Template Catalog and a static machine-readable Template Catalog;
- faithful A4 browser previews and Reference PDFs;
- source-file and install-command copy actions;
- the Clearline and Signal Ledger proof templates;
- contribution, provenance, validation, release, compatibility, deprecation, and removal rules.

The two proof templates are the launch minimum. More templates MAY ship after they pass the same contribution and acceptance rules.

V1 does not include an editor, user accounts, saved CV Data, application persistence, an npm package containing all templates, US Letter output, deployment-provider configuration, or custom-domain configuration.

Product identifiers and website text use English. CV Data accepts Unicode content in any language. V1 supplies fixed English and French generated labels and acceptance fixtures. Layout guarantees cover left-to-right languages.

Priority is developers and software agents equally, then contributors, then Catalog visitors.

## 2. Contract authority and versions

The published schemas and this specification define compatibility. Accidental implementation behavior is not a contract.

V1 publishes these immutable JSON Schema Draft 2020-12 documents:

```text
/schemas/cv-data/v1.json
/schemas/fidelity-envelope/v1.json
/schemas/template-catalog/v1.json
/schemas/cv-ui-meta/v1.json
/schemas/provenance/v1.json
/schemas/release-manifest/v1.json
/schemas/removal-tombstone/v1.json
```

Each schema MUST:

- use its absolute `https://cv-ui.alfredmouelle.com` URL as `$id`;
- declare `https://json-schema.org/draft/2020-12/schema`;
- resolve every `$ref` from its own `$defs`;
- set `additionalProperties: false` on each contract object, except opaque extension payload objects;
- avoid the JSON Schema `format` keyword;
- use `Cache-Control: public, max-age=31536000, immutable`;
- remain outside Releases and have no unversioned alias.

Runtime rules in this document are authoritative where JSON Schema cannot express a rule. Examples include real calendar dates, standards-based format parsing, cross-field order, Unicode algorithms, document totals, and cross-entry Catalog rules.

CV Data uses major string versions. V1 is `"1"`. Catalog, metadata, provenance, Release Manifest, removal tombstone, and Fidelity Envelope documents use `"1.0"`.

## 4. CV Data V1

### 4.1 Meaning and root

`CvDataV1` describes one publishable CV. It is not a master career profile, editor state, or presentation configuration.

The root is a closed object. It has this field order and shape:

```ts
type CvDataV1 = {
  readonly schemaVersion: "1";
  readonly language: string;
  readonly person: CvPersonV1;
  readonly summary?: string;
  readonly work?: readonly CvWorkV1[];
  readonly education?: readonly CvEducationV1[];
  readonly projects?: readonly CvProjectV1[];
  readonly skills?: readonly CvSkillV1[];
  readonly languages?: readonly CvLanguageV1[];
  readonly certifications?: readonly CvCertificationV1[];
  readonly awards?: readonly CvAwardV1[];
  readonly volunteer?: readonly CvVolunteerV1[];
  readonly publications?: readonly CvPublicationV1[];
  readonly extensions?: CvExtensionsV1;
};
```

The minimum valid document is:

```json
{
  "schemaVersion": "1",
  "language": "en",
  "person": { "name": "A" }
}
```

All other human-facing fields and sections are optional. Missing fields MUST be omitted. `null`, empty arrays, and strings containing no non-whitespace character are invalid.

All authored text is plain Unicode. Markdown and HTML are invalid content.

A normal URL MUST be an absolute WHATWG URL with `http:` or `https:`. A semantic reference URI MUST be absolute under RFC 3986 and MAY contain a fragment. Rendering MUST NOT resolve a semantic reference URI.

`CvPartialDateV1` accepts only real proleptic-Gregorian dates in years 0001 through 9999 with one of these forms: `YYYY`, `YYYY-MM`, or `YYYY-MM-DD`. A partial date denotes its complete calendar interval. An `end` or `expires` value is invalid only when its latest possible day precedes the earliest possible day of its related start or issue date. `qualificationReference` requires `qualification`. `expires` requires `date`.

Arrays preserve authored order. Repeated records have no IDs. CV Data has no `sectionOrder` or presentation configuration.

### 4.3 Extensions

```ts
type CvJsonValueV1 =
  | null
  | boolean
  | number
  | string
  | readonly CvJsonValueV1[]
  | { readonly [key: string]: CvJsonValueV1 };

type CvExtensionsV1 = Readonly<
  Record<string, Readonly<Record<string, CvJsonValueV1>>>
>;
```

An extension key MUST contain at least three lowercase ASCII DNS-style labels. Each label has 1 to 63 characters, permits an interior hyphen, and cannot start or end with a hyphen. The full key has at most 253 characters. Each extension value is a JSON object. The core validator treats its contents as opaque JSON.

V1 CV Templates MUST NOT require or render an extension. They ignore unknown extensions. A later shared contract can define optional rendering and Fidelity Envelope limits for an extension.

### 4.5 CV Data errors and traversal

```ts
type CvDataValidationError =
  | { readonly path: string; readonly code: "required" }
  | { readonly path: string; readonly code: "unexpected-field" }
  | {
      readonly path: string;
      readonly code: "invalid-type";
      readonly expected:
        | "null"
        | "boolean"
        | "number"
        | "string"
        | "array"
        | "object"
        | "json-value";
      readonly actual:
        | "null"
        | "boolean"
        | "number"
        | "string"
        | "array"
        | "object"
        | "undefined"
        | "bigint"
        | "symbol"
        | "function"
        | "non-finite-number";
    }
  | {
      readonly path: string;
      readonly code: "invalid-literal";
      readonly expected: null | boolean | number | string;
      readonly actual: null | boolean | number | string;
    }
  | { readonly path: string; readonly code: "empty-value" }
  | {
      readonly path: string;
      readonly code: "invalid-format";
      readonly format:
        | "bcp47"
        | "email"
        | "http-url"
        | "absolute-uri"
        | "partial-date"
        | "extension-namespace";
    }
  | {
      readonly path: string;
      readonly code: "invalid-order";
      readonly relatedPath: string;
    }
  | {
      readonly path: string;
      readonly code: "missing-dependent-field";
      readonly relatedPath: string;
    };
```

Errors have no message field. Paths use RFC 6901 JSON Pointer. The root is `""`. Missing fields use their would-be path.

Validation walks depth first. It visits known properties in the contract order in this section, array items by index, then unknown properties by Unicode scalar-value order. Extension namespaces and arbitrary extension object keys also use scalar-value order. It MUST NOT use JavaScript property enumeration, UTF-16 sorting, locale collation, or a final error sort.

A type failure suppresses child, literal, empty, format, and relationship checks for that value. A required or unexpected field emits one error. An unexpected value is not traversed. A wrong literal emits `invalid-literal`, including for an empty string. An empty general string or array emits `empty-value` and suppresses its format and relationship checks. A format failure suppresses dependent relationship checks. Relationship errors follow the fields they inspect.

Format algorithms are fixed:

- whitespace uses Unicode 17.0 `White_Space`;
- language tags use RFC 5646 `Language-Tag` ABNF, case-insensitive, without registry checks;
- email uses the single-address WHATWG HTML Email-state grammar at snapshot `c46c0c7a362e46b49f087957b6eb071ad253f8ed`;
- HTTP URLs use the WHATWG basic URL parser at snapshot `55d6699373ba68a16ec182f34222a74ed8bc3dac`, without a base;
- semantic URIs use RFC 3986;
- JSON Pointer uses RFC 6901.

## 5. Fidelity Envelope V1

Every V1 CV Template MUST render every valid CV Data document inside this single envelope. A template cannot define different limits or request an exemption.

```ts
const CV_FIDELITY_ENVELOPE_V1 = {
  schemaVersion: "1.0",
  unicodeVersion: "17.0",
  graphemeAlgorithm: "UAX29-47",
  page: { format: "A4", maximumPages: 2 },
  textLimits: {
    compact: 40,
    label: 80,
    nameOrTitle: 120,
    highlight: 180,
    entrySummary: 320,
    profileSummary: 600,
    unbrokenText: 40,
  },
  collectionLimits: {
    personLinks: 5,
    work: 4,
    education: 4,
    projects: 4,
    certifications: 4,
    awards: 4,
    volunteer: 4,
    publications: 4,
    skills: 8,
    skillKeywords: 8,
    languages: 6,
    publicationAuthors: 10,
    recordHighlights: 5,
  },
  documentLimits: {
    records: 14,
    highlights: 24,
    authoredText: 5000,
  },
} as const;
```

Text mappings are exact:

- `compact`: education score, skill level, each skill keyword, language fluency;
- `label`: email, phone, every location, link label, certification credential ID;
- `nameOrTitle`: person name, headline, organization, position, role, institution, qualification, field, project name, skill name, language name, certification name, issuer, award title, publication name, publisher, each publication author;
- `highlight`: each highlight;
- `entrySummary`: work, volunteer, project, publication, and award summary;
- `profileSummary`: root summary;
- `unbrokenText`: every visible authored string segment without an allowed Unicode line-break boundary.

The `records` total counts top-level work, education, project, skill, language, certification, award, volunteer, and publication records. It excludes person links, keywords, authors, and highlights. `highlights` counts all record highlights.

`authoredText` counts each supplied human-facing core string occurrence once as stored, including partial-date strings. It excludes schema metadata, document language, language codes, semantic references, URL targets, extensions, generated labels, formatted dates, separators, and repeated display of one input value.

Grapheme counts use Unicode 17.0 extended grapheme clusters under untailored UAX #29 revision 47 without normalization or host Unicode data. Unbroken segments use Unicode 17.0 and untailored UAX #14 revision 55, rules LB1 through LB31, with no dictionary breaking, locale rules, hyphenation, or emergency breaks. A boundary inside a grapheme cluster is discarded.

```ts
type CvFidelityErrorCode =
  | "text-length"
  | "unbroken-text"
  | "array-count"
  | "record-count"
  | "highlight-count"
  | "authored-text";

type CvFidelityError = {
  readonly path: string;
  readonly code: CvFidelityErrorCode;
  readonly limit: number;
  readonly actual: number;
};
```

The validator emits `array-count` before visiting array items. A string emits `text-length` before `unbroken-text`. Field and collection errors follow CV Data traversal. Document totals follow all other errors in this order: `record-count`, `highlight-count`, `authored-text`.

The Fidelity Envelope validator does not predict pagination. Valid envelope data that produces more than two pages is a CV Template failure. Invalid envelope data MUST fail before the component returns output and MUST produce no partial DOM, PDF, or PNG.

## 6. CV Template authoring contract

### 6.1 React and exports

A CV Template is a deterministic, server-compatible React component. It has one public named export. The name is the PascalCase Template ID plus `Cv`. Its only prop is `{ readonly data: CvData }`.

Clearline exports `ClearlineCv`. Signal Ledger exports `SignalLedgerCv`. There are no default exports, exported prop types, barrels, styling props, section-order props, routes, pages, global CSS edits, or configuration edits.

The component imports its CSS. It runs CV Data and Fidelity Envelope validation before returning output.

Template code MUST NOT use:

- `"use client"`;
- hooks, context, portals, state, effects, or event handlers;
- browser globals, direct DOM access, storage, or network access;
- remote resources or asynchronous data loading;
- randomness, current time, or environment-dependent content;
- DOM measurement branching or template-owned pagination;
- canvas, text in SVG, images of text, `dangerouslySetInnerHTML`, or CSS-generated CV text.

Internal pure helper components are permitted.

### 6.2 Required HTML

Each output MUST have:

- one root `article` with `lang` from CV Data and `data-cv-template="<template-id>"`;
- one `h1` for the person name;
- one `h2` for each rendered CV Data section;
- `h3` for titled section records;
- semantic lists for repeated records, highlights, skills, languages, and links;
- one `address` for contact information;
- real web, mail, and telephone anchors;
- `time` with `datetime` for exact dates;
- `data-cv-section="<section-id>"` on each CV Data section;
- `data-cv-entry="<section-id>.<zero-based-index>"` on each record;
- `data-cv-highlights` on each highlight list.

Signal Ledger Contact is a presentation-only Contact Group built from `person` fields. It is not a CV Data section and has no `data-cv-section` marker. Its English and French label is `Contact`.

Every supplied human-facing core value MUST appear once in DOM reading order. URLs MAY appear only as targets when a supplied label or related value names the link. Schema version, language, semantic references, and ignored extensions need not appear.

DOM order, visible reading order, and PDF text-extraction order MUST match.

### 6.3 CSS, print, and accessibility

Use Tailwind utilities in JSX for ordinary styling. The template CSS file is limited to owned fonts, physical A4 geometry, named page rules, print rules, and pagination controls.

The root selector and named `@page` derive from the Template ID. Font-family names use `cv-ui-<template-id>-`. Ordinary selectors remain below the root.

Template CSS MUST NOT use `@import`, global element selectors, `:root` changes, global Tailwind layers, `!important`, hidden supplied content, undeclared resources, or remote resources. Generated installation CSS MAY replace a declared template-owned WOFF2 URL with a `data:font/woff2;base64,...` URL. The decoded bytes MUST equal the canonical font bytes. Other data URLs are invalid.

Use physical units for A4 and print margins. CV text and links stay at least 10 mm from each page edge. Text-free backgrounds and decoration MAY reach the edge.

Grid and flex are allowed. CV text MUST NOT use absolute, fixed, or sticky positioning. Content containers MUST NOT use fixed heights, clipped or scrollable overflow, CSS multi-column flow, or transforms. Positioned decorative elements contain no text, link, or semantic content.

All visible text is at least 8 pt. Primary prose is at least 9 pt. Line height is at least 1.2. Text meets WCAG AA contrast. Color does not carry meaning alone.

Validation rejects unnamed links, heading-level skips, duplicate IDs, invalid language tags, inaccessible SVG, lost reading order, missing content, and duplicated authored content.

## 7. A4 output and preview fidelity

Every page is exactly 210 mm by 297 mm. Printing uses zero browser margin, 100% scale, background graphics, and no browser headers or footers. Each template owns its internal margins.

All fonts and assets are local CV Registry Item resources. A font embedded in generated installation CSS is local. Capture waits for font and image completion. A missing asset, undecoded image, substituted font, or unembedded PDF font fails.

Pinned Chromium normal document flow owns pagination. Templates MUST NOT calculate page breaks. A record moves intact to the next page when it fits there. It MAY split only when taller than a complete page content area. A section heading stays with the content it introduces.

Validation rejects clipping, unintended overlap, blank pages, changed content order, orphan headings, and nondeterministic page count or breaks. Geometry checks allow at most one CSS pixel for edge contact, clipping, and unintended overlap. Structural values and raster pixels remain exact.

The Reference PDF produced by the qualified pinned Chromium build defines correct rendering. Visible text remains selectable and searchable. Extracted text contains every visible string in DOM order. Web, email, and phone links remain active. Every font is embedded.

The Catalog Preview is the ordered English Reference Output page set. Each page is a lossless 144 DPI PNG, 1191 by 1684 pixels after rounding. The UI reserves the aspect ratio, scales pages down uniformly on narrow containers, and never enlarges them above 100% of CSS A4 size. It does not crop or reflow the layout.

Current Firefox and Safari MUST show complete, readable Catalog previews. Exact print parity outside Chromium is not guaranteed. Pinned Playwright Firefox and WebKit builds MUST show finite layouts without clipping, console errors, or resource errors. Maintainer review checks current Safari.

Physical printer output, CMYK, PDF/A, bleed, crop marks, custom page sizes, and US Letter are out of scope.

### 11.3 Discovery

Catalog search inspects name, summary, Controlled Trait literals, and reviewed Search Aliases. It excludes IDs, paths, author names, and license text.

Normalize the query and every indexed value with this fixed Unicode 17.0 process:

1. Apply NFKD.
2. Apply full default case folding.
3. Remove every code point with General Category Mark.
4. Map each remaining character outside ASCII `a` through `z` and `0` through `9` to U+0020.
5. Collapse space runs.
6. Trim.
7. Split on U+0020 into tokens.

Every query token MUST match a complete indexed token or an indexed token prefix. All query tokens must match. Search has no fuzzy correction and does not change sort order.

Filters are layout, ATS intent, visual tone, density, and photo support. Selection uses OR inside one dimension and AND across dimensions. The UI shows counts, disables unavailable unselected values, and keeps selected zero-count values visible.

Default sort is `catalogOrder`, English name, then ID. Name sort is English name, then ID. Default results hide deprecated templates. A direct detail route and explicit direct result can still expose a deprecated template.

### 11.4 Catalog route

The Catalog route is `/templates`. Query keys use this order:

1. `q`
2. repeated `layout`
3. repeated `ats`
4. repeated `tone`
5. repeated `density`
6. repeated `photo`
7. `sort`

Repeated values follow contract order and collapse duplicates. `sort=name` selects name sort. Default Catalog order is implicit. `sort=catalog` is omitted.

Search text is trimmed and whitespace runs collapse before storing `q`. Encoding uses UTF-8 `URLSearchParams`, including `+` for spaces. Empty search, empty filter dimensions, and default sort are absent.

Discovery changes replace the current history entry. Opening a template creates a new entry. Browser Back restores the exact Catalog URL. Unknown keys and values do not affect results and are removed on the next internal URL update. An empty result preserves state and offers one clear-all action.

### 11.5 Detail route and copy behavior

The detail route is `/templates/<template-id>`. Unknown IDs use the normal not-found page.

Query keys are:

1. `mode=code|info`, with Preview implicit;
2. `file=<basename>`, valid only in Code mode, with the first file implicit.

V1 has no `lang` query. Preview shows the English Reference Output. English and French still have equal validation coverage in the Acceptance Corpus.

Preview, Code, and Info are the three modes. Code shows files in component, CSS, then installed-example order. Info shows canonical Catalog and installation facts. Invalid or default values are removed on the next internal update. Mode and file changes replace the current history entry.

Code mode copies only the complete selected file. There is no copy-all action. Changing file or mode clears prior source-copy status.

The install panel copies the selected command and always exposes the named and direct HTTPS commands plus `view` and `--dry-run`. CV UI does not infer CLI failure. The user selects the fallback.

A copy action reports `Copied` only after the Clipboard promise resolves. On rejection, the exact source remains visible, receives focus and selection, and reports: `Copy failed. Select the text, then press Ctrl+C or Command+C.` It MUST NOT use a deprecated clipboard fallback.

Copy state has no timer. It remains until the user changes the command, source file, or detail mode.

At 1024 px and wider, the install panel is sticky beside active output. Below 1024 px, a fixed `Install` action opens a sheet with the same commands and facts. The sheet traps focus. Close, Escape, and backdrop click dismiss it and return focus to `Install`. Copy keeps it open. Route navigation closes it. Sheet state is not in the URL.

The untrusted CI workflow runs for pull requests to `main`, `merge_group` checks, and pushes to `main`. Pull requests receive a read-only token and no secrets. CI uses `pull_request`, not `pull_request_target`, for untrusted code.

Jobs are:

4. `governance`, which evaluates DCO, provenance, resources, notices, and maintainer acceptance without executing pull-request code.

A Release contains all registry items, supported Catalog documents, Reference PDFs, preview PNGs, and current removal tombstones from one source commit. The full lowercase 40-character source commit SHA is its Release ID.

Files use `/releases/<release-id>/<relative-path>`. The manifest is `/releases/<release-id>/manifest.json`.

A Release Candidate comes from an explicitly selected protected `main` commit with successful `CI / required`. A clean checkout with the frozen lockfile runs all five CI commands before promotion.

### 15.1 Release Manifest

Artifacts are non-empty, path-sorted, and path-unique. Paths are relative, use `/`, and contain no leading slash or empty, `.` or `..` segment. Size is the exact non-negative byte count. SHA-256 is 64 lowercase hexadecimal characters and matches published bytes. Every Release file except `manifest.json` appears once.

The manifest excludes itself, schemas, Stable Aliases, and the Current Release pointer.

### 15.2 Promotion

Promotion jobs serialize and do not cancel after upload starts:

1. Upload the complete immutable Release.
2. If the namespace exists, resume only when every existing byte matches.
3. Verify the public manifest and every artifact.
4. Change the Current Release pointer with compare-and-swap against the expected previous Release.
5. Purge Stable Aliases.
6. Run post-promotion checks.

The internal pointer records schema version, current Release ID, optional previous Release ID, manifest URL, and manifest digest. It is not a public API.

Immutable files use `Cache-Control: public, max-age=31536000, immutable`. Stable Aliases use `Cache-Control: public, max-age=0, must-revalidate`, a strong artifact `ETag`, and `X-CV-UI-Release` with the full Release ID.

A failure before pointer change leaves the previous Release current. A failure after pointer change restores the verified previous pointer. A missing or digest-invalid Current Release artifact returns 503 and starts rollback. It MUST NOT mix in an artifact from another Release. A failed alias purge restores the previous pointer, purges again, and verifies aliases. Immutable files are never repaired or overwritten. Stable Aliases return 503 before the first successful promotion.

Maintainers announce only after the pointer selects the intended commit, all artifacts match the manifest, uncached aliases pass, both installation paths work, the Catalog loads, and all Reference Outputs return.

## 16. Compatibility, deprecation, and removal

CV Data supports the current and previous major. Adjacent migrations are explicit named zero-dependency functions, such as `migrateCvDataV1ToV2`. Validation and rendering never migrate silently. A migration accepts every valid prior document and preserves authored values, order, date precision, language, and opaque extensions.

A Template ID keeps its design and public component contract. Compatible revisions preserve export, prop, installed paths, supported CV Data majors, and design identity. A major redesign or incompatible component contract gets a new Template ID. A template can add a CV Data major but cannot drop a previously supported major.

Catalog schema versions use `major.minor`. Additive optional fields increment minor. Removal, rename, meaning change, or stricter requirement increments major. Retained endpoints include `/catalog/v1/templates.json`. `/catalog/templates.json` aliases the current major. Every published major endpoint remains.

The stable `/r/<template-id>.json` contract preserves its original shadcn and `meta.cvUi` fields. Compatible bytes can change. Incompatible registry representation requires a major-specific endpoint while retaining the V1-compatible endpoint.

Deprecation adds a reason, real date, and optional replacement Template ID. It preserves the registry item, Reference Output, install URL, detail route, and direct result. Default Catalog results hide it.

Removal is allowed only for legal risk, security risk, or an artifact CV UI cannot redistribute. It never permits ID reuse.

```ts
type RemovalTombstoneV1 = {
  readonly schemaVersion: "1.0";
  readonly templateId: string;
  readonly status: "removed";
  readonly reason:
    | "legal-risk"
    | "security-risk"
    | "redistribution-unavailable";
  readonly removalDate: string;
  readonly replacementTemplateId?: string;
};
```

The removal date is the immutable UTC date the tombstone first becomes current. A replacement is different and names an active template in the same Release. The machine document contains no free-text detail.

The current Release stores the tombstone at `r/<template-id>.json` and inventories it as JSON. Its immutable URL returns 200. The Stable Alias returns the same bytes with 410, normal ETag, and Release header. Current Catalog documents omit the removed entry. The human detail page remains with the same safe facts.

Removal is the only exception to complete historical Release availability. Older registry, PDF, preview, and related URLs for the removed template return the current tombstone or 410 as applicable. Old manifests remain unchanged, but suppressed paths cannot be verified. Unrelated historical artifacts remain immutable and available.

Compatibility fixtures cover each published CV Data major, Catalog major, registry schema major, and Template ID. CI checks old valid data, migrations, retained metadata, supported majors, permanent paths, and tombstones.
